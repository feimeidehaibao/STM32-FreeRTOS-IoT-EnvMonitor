# 基于 STM32F103 + FreeRTOS 的物联网环境监测终端

## 📌 项目简介
本项目是一个多任务的物联网数据采集与上报终端。主控采用 STM32F103C8T6，实时操作系统采用 FreeRTOS (CMSIS-OS V1 封装)。实现的功能包括：
1.让OLED屏拥有两个数据显示模式，分别选择显温湿度数据或者光照强度数据，在程序启动的初期是默认显示温湿度数据。在核心板上按下KEY2可以实现两种显示模式的切换 
2.ESP8266模块可每隔一秒来向tcp客户端发送温湿读数据和光照强度数据，同时也可以通过ESP8266在tcp客户端远程发送指令来切换oled的数据显示模式，发送“wen"可让oled屏显示温湿度数据，发送”guang“可让oled屏显示光照强度数据。  
3.每隔六十秒就会将当前的温湿度数据和光照强度数据存入flash模块的第一个扇区中，以防止断电断网后丢失数据无法找回。

## 🏗️ 软件架构设计
系统采用 **BSP (底层驱动) / Module (模块封装) / APP (业务逻辑)** 三层解耦架构，便于后期维护与移植。
- **Task_Display (优先级 2)**：负责按键扫描与 OLED 页面刷新。
- **Task_Comm (优先级 3)**：负责 ESP8266 状态机维护、TCP 数据上报与云端指令解析。
- **Task_Storage (优先级 1)**：负责将传感器数据存入 W25Q64 Flash。

## 🚀 核心难点与踩坑复盘 (Engineering Highlights)

在项目开发过程中，遇到了多个底层的系统级异常，以下是排查与解决过程的记录：
1. **SysTick 抢占问题（提前避坑）**

   - **问题背景**：我在程序建立初期并没有真正遇到这个 Bug，而是在准备移植 RTOS 之前看教程就提前了解到了这个致命冲突。
   - **解决方案**：在 CubeMX 软件里建立初始化工程时，我特意将 `Timebase Source`（时基源）选项主动从 `SysTick` 改成了 `TIM1`。在 RTOS 成功移植后，我将 `stm32f1xx_it.c` 中的 `SysTick_Handler`、`PendSV_Handler` 和 `SVC_Handler` 三个函数全部注释掉，再将初始化工程中的 `TIM1_UP_IRQHandler` 移植了过来。
   - **最终效果**：不仅预防了中断函数重名冲突，还将 HAL 库的时基来源改成了 `TIM1`，彻底把 `SysTick` 让给了 RTOS 程序调度使用。

2. **未使能 TIM 模块导致编译报错**

   - **现象**：在 `stm32f1xx_it.c` 中引入 `TIM1_UP_IRQHandler` 之后出现了编译错误。日志显示找不到 `HAL_TIM_IRQHandler` 和 `HAL_TIM_Base_Init` 等函数。
   - **排查推导**：一开始以为是没把源文件加进工程，但即使把 `stm32f1xx_tim.c` 加进去了，依然无法解决报错。
   - **解决方案**：之后打开 `stm32f1xx_hal_conf.h`，发现了其中的 `#define HAL_TIM_MODULE_ENABLED` 被默认注释掉了（这是 HAL 库为了裁剪体积的机制）。将该模块进行手动使能后，才编译成功。

3. **堆内存分配失败与任务栈溢出 (OOM)**
   - **现象**：程序编译无误，但烧录后完全无法运行。OLED 不亮，WiFi 没反应，串口也没有任何输出。
   - **排查过程**：
     - 第一步：注释掉 WiFi 和 Flash 任务，只保留 OLED 任务，并加入 `printf` 探针，发现 OLED 正常运行。
     - 第二步：恢复 Flash 任务，加入探针，发现 OLED 与 Flash 均能并发运行。
     - 第三步：恢复 WiFi 任务，系统直接死机。此时判定问题出在 WiFi 任务上。
     - 第四步：让 WiFi 脱离 RTOS 单跑（裸机），发现能正常连网，排除底层代码问题，锁定为 RTOS 内存资源分配不足。
   - **解决方案**：打开 `FreeRTOSConfig.h`，发现默认的 `configTOTAL_HEAP_SIZE` 仅为 3448 字节，无法支撑多任务。将其扩大至 10240 字节；同时将 WiFi 任务的栈空间增至 512 Words（2KB），OLED 和 Flash 设为 256 Words。
   - **复盘总结**：WiFi 任务中包含了 ESP8266 初始化、TCP 通信、AT 指令解析以及浮点数格式化的 `snprintf`，函数嵌套极深、栈消耗极大。原本 256 Words 的栈绝对不够用，必须扩容。

4. **I2C 硬件总线死锁与任务周期优化**
   - **现象**：在频繁复位或拔插电源时，OLED 会突然黑屏，串口疯狂打印 `OLED_WriteByte 写入失败`，系统卡死。即使断电重启也无法让OLED模块恢复运行，这使我一度以为OLED模块炸了，最后是去烧录了其他的OLED显示程序才让该模块恢复运行
   - **排查推导**：主机（STM32）复位时，若从机（OLED）刚好在发送 ACK 拉低 SDA 线，主机会误判总线被占用而一直死等（I2C 死锁）
   - **解决方案**：在底层加入超时机制（10ms 退出），并在OLED驱动层中的I2C发送字节的函数中添加了失败重启功能：若连续发送失败达到五次，则会立刻执行OLED初始化和重启程序，从而保证OLED显示模块长时间正常运行

5. **多任务抢占导致的全系统崩溃**

   - **现象**：系统好不容易跑起来后，表现得极度不稳定。具体表现为：WiFi 模块频繁断连；只要在手机 TCP 客户端发送任何指令（如 `guang`），WiFi 立刻掉线导致无法远程切屏；OLED 模块频繁报错（`OLED_WriteByte 写入失败`）并触发底层重启；甚至连光敏模块的光照强度数据都无法读取。
   - **排查推导**：三个模块可以各自正常运行，初步推测为RTOS任务协调问题。结果发现OLED显示模块的阻塞时间仅为20ms，比更高优先级的WiFi模块的阻塞时间50ms还要短，而I2C 硬件刷一次全屏可能就需要耗时 20~30ms，同时阻塞时间过短也会导致ready时间过短，所以导致了OLED显示模块几乎一直霸占着 CPU，别的任务根本抢不到时间片。并且WIFI模块的优先级大于OLED显示模块，容易出现OLED在刷新全屏的时候被强行打断来强制执行WIFI连接和传输任务，所以也容易出现OLED频繁报错的问题
   - **解决方案**：将OLED显示模块的阻塞时间从 20ms 改到100ms。虽然理论上刷新率降低了，但肉眼看起来毫无区别。改完之后，WiFi 瞬间稳定，长链接不再断开，指令也能秒接收，光照数据也恢复正常了，系统彻底稳定下来。
   - **复盘总结**：在给任务设置阻塞时间的时候需要考虑实行任务所需的时间和优先级，如果阻塞时间过短，容易导致一些复杂的任务出现问题
   
## 🔧 硬件与工具链
- **MCU**: STM32F103C8T6 (ARM Cortex-M3)
- **RTOS**: FreeRTOS (CMSIS-OS V1)
- **传感器/外设**: DHT11, 光敏电阻, 0.96寸 OLED (I2C), ESP8266 (AT指令), W25Q64 (SPI)
- **开发环境**: Keil MDK, STM32CubeMX
